Agent Skills, across all three surfaces

A Skill is a folder — instructions, scripts, reference files — that gives Claude an on-demand specialty. The same SKILL.md format shows up in three different runtimes: the raw Messages API, the Claude Code terminal, and your own product built on the Agent SDK. This page compares the three side by side, shows how to build each, and maps the pattern onto banking and finance work.

01 · Core concept

What a Skill actually is

Before comparing the three surfaces, one mechanism explains all of them: progressive disclosure. A Skill is not injected into the prompt wholesale — Claude reads more of it only as the task proves it's relevant.

Every Skill is a directory containing a required SKILL.md file. That file has two parts: YAML frontmatter (a name and a description — the description has to state both what the Skill does and when to use it, since that's the only text Claude sees before deciding to load the rest) and a Markdown body with the actual instructions. The folder can also hold extra reference files (FORMS.md, REFERENCE.md) and executable scripts.

Two consequences follow directly from this diagram, and both matter for a regulated environment like a bank:

  • Cost scales with relevance, not with what you've installed. You can enable dozens of Skills — a bank might have one per product line — without the system prompt ballooning, because only the name + description pair of an unused Skill ever loads.
  • Deterministic steps belong in scripts, not prose. A Python script that computes a debt-service-coverage ratio and a paragraph asking Claude to compute it by reasoning give very different reliability guarantees. Executing the script is the pattern the Skill format is built to encourage — the code never enters context, only its printed result does.
Governance note

Anthropic's own guidance is explicit that a Skill should be treated "like installing software": audit the SKILL.md, every bundled script, and any URL it fetches before you enable it, especially anything sourced outside your organization. For a bank this maps directly onto existing third-party-code review and model-risk-management processes — a Skill is executable logic that touches customer data, not a passive prompt template.

02 · Orientation

The same file, three runtimes

The SKILL.md format doesn't change. What changes is who loads it, where it executes, and who is holding the other end of the conversation — a raw API caller, a developer at a terminal, or your own application's users.

Skills + Claude API

for: backend engineers, platform teams

You call the Messages API directly. Skills are uploaded objects, attached per-request via container.skills, and executed inside an ephemeral, network-isolated sandbox alongside the code-execution tool.

Skills in Claude Code

for: developers, in a repo or terminal

Skills are files on disk (~/.claude/skills or .claude/skills) that Claude Code discovers automatically. You author them interactively and invoke them by typing /name or by asking a matching question.

Skills + Agent SDK

for: teams building a custom agent product

Same filesystem-based Skills as Claude Code, but embedded inside your application via query(). You control exactly which Skills the embedded agent is allowed to invoke.

03 · Surface one

Skills with the Claude API

This is Skills as a server-side capability: your own backend calls the Messages API and attaches Skills the way it would attach a tool. No terminal, no interactive session — a stateless request that returns a document, a computation, or a formatted file.

When to use it

reach for it when
  • You're building a product feature that calls Claude programmatically (a loan-origination service, a customer-facing chatbot, a batch job).
  • The task benefits from Anthropic's built-in document Skills — pptx, xlsx, docx, pdf — or a custom Skill you want versioned like an artifact.
  • You need workspace-wide sharing: one Skill, every service in your org's API workspace can attach it.
skip it when
  • A developer needs the Skill while coding — that's Claude Code, not a raw API call.
  • You're shipping your own branded agent product with a UI — the Agent SDK gives you that scaffolding for free.
  • The task needs live network access from inside the Skill's sandbox — the code-execution container has none.

How it works

A Skill on the API surface is attached through the container parameter of a messages.create call, and it always runs alongside the code-execution tool — Skills and code execution share the same sandbox, which is why the tool is a hard requirement, not an option.

# 1. List Anthropic-managed skills
ant skills list --source anthropic
# -> pptx, xlsx, docx, pdf
# 2. Attach a skill to a request and require code execution
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    container={
        "skills": [{"type": "anthropic", "skill_id": "pptx", "version": "latest"}]
    },
    tools=[{"type": "code_execution_20250825", "name": "code_execution"}],
    messages=[{"role": "user", "content":
        "Create a 5-slide presentation summarizing Q3 NPL trends."}],
)

# 3. Pull the generated file back out of the response
for block in response.content:
    if block.type == "bash_code_execution_tool_result":
        for out in block.content.content:
            file_id = out.file_id

client.files.download(file_id=file_id).write_to_file("q3_npl_review.pptx")

For a Skill your organization authors — a house style, an internal calculation, a regulated document template — you register it once and reuse a stable identifier:

# Upload a custom skill bundle (zip or file list), then pin a version
skill = client.skills.create(name="credit-memo", files=files_from_dir("./credit-memo/"))
version = client.skills.versions.create(skill_id=skill.id, files=files_from_dir("./credit-memo/"))

container = {
    "skills": [{"type": "custom", "skill_id": skill.id, "version": version.id}]  # pinned, not "latest"
}

A few operational details that matter for a bank running this in production: up to 20 Skills per request; each Skill's files land at /skills/{name}/ inside the container; the sandbox has no network access and can't install packages at runtime, which is exactly the isolation property a data-governance review will ask about; pin an exact version for production traffic and reserve "latest" for development, so a Skill update never silently changes behavior in a live loan-decisioning pipeline; and Skills aren't priced separately — they're consumed as ordinary token and code-execution usage, but changing the attached Skill list invalidates prompt caching for that request shape.

Banking example

Automated credit memo generation. A custom credit-memo Skill bundles the bank's approved memo template, the DSCR/LTV calculation logic as a Python script, and the house style for risk commentary. The loan-origination backend calls the Messages API once per approved application with the applicant's financials in the prompt and container.skills=[credit-memo]; Claude runs the ratio script (deterministic, auditable), drafts the narrative, and returns a formatted Word file via file_id — no human touches a template.

Banking example

Nightly regulatory disclosure pack. A batch job in the bank's data platform attaches the built-in xlsx Skill plus a custom basel-disclosure Skill to turn a risk-weighted-assets extract into the bank's formatted capital-adequacy workbook — run inside a network-isolated container so the extract never leaves the request boundary.

04 · Surface two

Skills in Claude Code

This is Skills as developer tooling: a folder on disk that Claude Code discovers automatically, invoked either by Claude itself when your request matches, or by you typing /skill-name. It's the fastest surface to author on and the one most engineers meet first.

When to use it

reach for it when
  • You keep re-pasting the same checklist, review steps, or domain context into chat — that's the signal a Skill should exist.
  • A section of your CLAUDE.md has grown from a fact into a multi-step procedure — Skills load on demand, so it stops costing tokens on every turn.
  • You want the procedure to travel with the repo (project Skill) or with you across every repo (personal Skill).
skip it when
  • The capability needs to run headless, inside a product you're shipping to customers — that's the API or the SDK.
  • It's a one-off instruction for this conversation only — just say it; a Skill is for something you'll need again.

How to build one

  1. Create the folder — personal (~/.claude/skills/<name>/) applies to every project; project (.claude/skills/<name>/) applies to this repo only.
  2. Write SKILL.md: YAML frontmatter with at least a description that states what it does and when to use it, then the Markdown instructions.
  3. Test it two ways — ask a matching question and let Claude auto-invoke, or type /skill-name directly.
mkdir -p ~/.claude/skills/summarize-changes
---
description: Summarizes uncommitted changes and flags anything risky. Use when
  the user asks what changed, wants a commit message, or asks to review a diff.
---

## Current changes

!`git diff HEAD`

## Instructions

Summarize the changes above in two or three bullets, then list any risks —
missing error handling, hardcoded values, tests that need updating.

The !`git diff HEAD` line is dynamic context injection: Claude Code runs that command and splices its live output into the Skill before Claude ever sees it, so the instructions arrive already grounded in your actual working tree rather than something Claude has to guess at.

Two frontmatter fields put a human hand on the automation, which matters most for anything with side effects:

  • disable-model-invocation: true — only a person can run it, via /name. Use this for anything with a side effect: /deploy, /send-payment-notice. You don't want Claude deciding to deploy because the code "looks ready."
  • user-invocable: false — only Claude can use it. Good for background domain knowledge, like a Skill that explains an internal ledger schema, that isn't a meaningful thing for a person to "run" directly.
Banking example

Enterprise-wide PCI review skill. A pci-lint Skill deployed through managed settings runs for every engineer touching the payments codebase, checking for logged PANs and missing encryption before a diff is committed — installed once by platform engineering, not per-developer, and it wins over any personal skill an individual engineer happens to have named the same thing.

Banking example

Personal, non-invocable context skill. An AI engineer keeps a feature-store-schema Skill with user-invocable: false in ~/.claude/skills/ — Claude consults it automatically whenever a conversation touches the credit-risk feature store, but nobody ever types /feature-store-schema, because it's reference knowledge, not an action.

05 · Surface three

Skills with the Claude Agent SDK

This is Skills embedded inside your own application. The SDK runs the same Claude Code engine under the hood, so it discovers the identical SKILL.md files from disk — but now you decide, programmatically, which ones the embedded agent may ever touch.

When to use it

reach for it when
  • You're building your own agent product — a copilot with its own UI, auth, and users — not calling the API from a stateless backend.
  • You want the terminal-grade agent loop (multi-turn, tool use, subagents) without asking every user to install Claude Code.
  • You need to lock the agent down to a vetted allowlist of Skills for a specific workflow, rather than "whatever's on disk."
skip it when
  • A single stateless document-generation call is all you need — that's the plain API surface, with less wiring.
  • You're the one at the terminal — just use Claude Code directly.

How it works

Skills are filesystem artifacts the same way they are in Claude Code — there is no programmatic "register a skill" API. What the SDK adds is control: the skills option on query() takes a list of names, "all", or [], and settingSources decides which directories are even discovered.

options = ClaudeAgentOptions(
    cwd=os.getcwd(),                       # where .claude/skills/ lives
    setting_sources=["user", "project"],   # load skills from disk at all
    skills=["kyc-refresh", "sar-narrative"], # allowlist — nothing else is reachable
    allowed_tools=["Read", "Grep", "Bash"],
)

async for message in query(
    prompt="Draft a SAR narrative for case 4471.", options=options
):
    print(message)

Three things trip up a first integration, and all three are captured in the troubleshooting section of the SDK docs:

  • Empty settingSources means zero Skills load — omitting the option keeps CLI-matching defaults, but explicitly setting settingSources: [] silently disables discovery.
  • cwd has to sit at or below the .claude/skills/ directory — the SDK walks up from cwd to the repository root looking for skill folders.
  • The skills allowlist takes exact names only — no wildcards. An unlisted Skill's files stay on disk and readable via Read/Bash, but the model can't see it and the Skill tool rejects an attempt to invoke it.

Restricting the allowlist doesn't restrict direct dispatch: sending the literal string /security-check in a prompt still runs a user-invocable Skill even if it's absent from your skills list — the allowlist governs what Claude decides to invoke on its own, not what you can call by name.

Banking example

AML investigator copilot. The bank builds its own case-management-integrated application on the Agent SDK. The embedded agent's skills list is locked to exactly two: transaction-pattern-lookup and sar-narrative-draft. allowed_tools is restricted to Read and Grep, so the copilot can inspect case files but can never execute arbitrary bash against a live investigation directory — the allowlist is the control an internal model-risk review will ask to see.

Banking example

Relationship-manager desktop copilot. A branch-facing tool built on the Agent SDK sets settingSources=["project"] and points cwd at a private repository of the bank's playbooks — KYC refresh steps, next-best-product logic — so relationship managers get the same terminal-grade agent loop developers use, with no local developer environment or Claude Code install involved.

06 · Orientation, again

Which surface do I actually reach for?

The three surfaces aren't competing options — most real deployments in a bank end up using all three for different jobs. The question is what's calling Claude.

What's calling ClaudeSurface
A backend service, batch job, or customer-facing product hitting the Messages API directlyClaude API
A developer, working interactively in a repo or terminalClaude Code
Your own application, with its own UI and users, that needs a full agent loop embedded in itAgent SDK
All three of the above, for the same organizationAll three — same SKILL.md, different wiring

Because Claude Code and the Agent SDK read the identical filesystem format, a Skill authored and tested at a developer's terminal can move into a shipped product with zero rewriting — only the options around it change. The API surface is the outlier: there, a Skill is a versioned, uploaded object rather than a local file, which is the right trade-off for something that has to run unattended in production at scale.

08 · Check yourself

Three questions

Answer in your own words before revealing each one.

Q1 A Skill folder bundles a 40-page REFERENCE.md. Why doesn't that file inflate your context window just because the Skill is enabled?
Because of progressive disclosure (Fig. 1). Only Level 1 — the name and description from the frontmatter, roughly 100 tokens — is always loaded, for every enabled Skill, in every session. The SKILL.md body (Level 2) loads only once the description matches the request. A separate file like REFERENCE.md (Level 3) loads only if the body explicitly points Claude to it for the task at hand — so a 40-page reference costs nothing until a request actually needs it, and even then, only the parts read.
Q2 Your loan-origination service calls the Messages API directly from a backend and needs to generate a Word credit memo on every approved application. Which surface, and what does the request have to include?
The Claude API surface — this is a stateless, programmatic caller, not a developer at a terminal or a custom agent product. The request must include a container.skills entry naming the Skill (the built-in docx, or a custom credit-memo Skill) and the code_execution tool in the tools list, since Skills on the API surface always run inside the code-execution sandbox — attaching a Skill without the tool won't work.
Q3 You want a pci-lint Skill to run for every engineer touching the payments codebase bank-wide, not something each engineer opts into individually. Which Claude Code skill location, and why does it beat a personal Skill with the same name?
The enterprise location, deployed through managed settings by an administrator. Per the precedence order in Fig. 3 — enterprise overrides personal, and personal overrides project — an enterprise-level pci-lint always wins a name clash against any individual engineer's personal copy in ~/.claude/skills/, which is exactly what guarantees every engineer runs the sanctioned version rather than whatever they happened to write for themselves.
